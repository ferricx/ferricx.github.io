Tab Navigation

Four tab sets built on the ARIA tabs pattern. Each has five tabs, and each tab panel holds a list of five links. The sets differ only in how the panel and the list inside it get their accessible names: the first leaves the list unnamed, the second names it with aria-labelledby pointing at the tab that owns the panel, the third names it with aria-label set to “Links for” followed by the tab's name, and the fourth keeps aria-labelledby on the list but removes the name from the panel. Compare how a screen reader reports the four.

WCAG 2.2 guidance

The lists in these panels have no accessible name. A screen reader announces only “list, 5 items”.

ARIA Authoring Practices, list named by its tab

The lists in these panels use aria-labelledby referencing their own tab, so each list is announced with the tab's name.

ARIA Authoring Practices, list named with aria-label

Same content as the set above, named a different way. Each list carries an aria-label of “Links for” followed by the tab's name, so the list's name is no longer the same string as the panel's name.

ARIA Authoring Practices, unnamed panel, list named by its tab

Same content again, attacking the duplicate from the other side. The tabpanel carries no aria-labelledby and so has no accessible name, while the list keeps aria-labelledby pointing at its tab. Only one element in the panel is named, so there is no second string for a screen reader to repeat.

Screen Reader Findings

Manual testing of the first two tab sets found that NVDA and VoiceOver disagree about which element carries the useful name, so the same markup helps one and hurts the other. Everything below was tested one way: keyboard tab navigation, moving focus from the tab into the panel. Browse mode, where a Windows screen reader reads through the page with the arrow keys, was not tested, and it is a separate code path in NVDA, so nothing here should be read as describing it. The third and fourth sets are attempts to work around the disagreement rather than further findings.

  • NVDA — Always announces the tabpanel's accessible name when focus moves into the panel. In the second set the list carries aria-labelledby pointing at the same tab, so the tab's label is announced twice, once as the panel's name and again as the list's name.
  • VoiceOver — Never announces the tabpanel's accessible name when focus moves into the panel. It does honor aria-labelledby on the <ul> and reads the list's name, so the second set is the only one where VoiceOver states which tab the links belong to. In the first set it announces neither name.
  • The tradeoff — Naming the list is the difference between context and no context in VoiceOver, and the difference between one announcement and a duplicated one in NVDA. Neither screen reader is wrong; they differ on whether a tabpanel's name is worth announcing, and the redundancy only appears when both names resolve to the same tab.
  • The workaround, third set — Since the redundancy comes from the two names being the same string, the third set gives the list a name of its own: aria-label of “Links for” followed by the tab's name. Both screen readers still announce exactly what the findings above describe, because aria-label and aria-labelledby feed the same accessible name computation and neither tool branches on which one produced the name. What changes is only the string, and the order matters: the new words come first and the repeated tab name comes last, so NVDA's second announcement signals it is not a repeat before the repeated part even arrives, rather than making the listener sit through an exact echo to find the one new word at the end. VoiceOver still gets the context it would otherwise lack. Not yet confirmed by testing.
  • The workaround, fourth set — Takes the other route: leave the two names identical but remove one of them, so the tabpanel has no accessible name and only the list is named. NVDA has nothing to repeat, since the panel it would otherwise name is unnamed, and VoiceOver is unaffected because it never announced the panel's name anyway. Both then read the same name, once each. This is the only set where the two tools agree.
  • Why the fourth set works — It works because the list is the tabpanel's only child. A name on the list names the list, not the panel that contains it, but here the two are effectively the same region, so moving the name from one to the other loses nothing. The list's own name is not fragile under keyboard navigation: it is announced when focus enters a link inside the list, and nothing added elsewhere in the panel would change that. What the precondition protects is the stronger claim, that the panel's name is redundant. That holds only while reaching the list and reaching the panel are the same event.
  • The name is reached on the way in — Because the list is the panel's only descendant, every focusable control in the panel is inside the list. Focus cannot enter the panel without entering the list, so Tabing in from the tab list announces the list's name as context before the link itself. That is what makes the missing panel name cost nothing here, under keyboard navigation: the association a panel name would have carried is announced anyway, on the way in.
  • What a sibling would cost, reasoning rather than a finding — Put a focusable control in the panel beside the list and it can be reached without passing through anything named, so nothing states which tab it belongs to. Non-focusable text raises a question the testing does not answer. A paragraph beside the list cannot be reached by Tab at all, only by reading through the page, and the panel's name is the one thing that could tie it to its tab. Whether either screen reader announces that name while reading through, rather than on focus, is untested and should not be assumed from the results above. Until that is checked, dropping the panel's name should be treated as having an unknown cost once the panel holds anything but the list.
  • Remaining costs of the fourth set — Dropping the panel's name substitutes for naming it only while the list is the whole panel. It also departs from the APG convention, and JAWS, Narrator, and TalkBack are untested here.

Accessibility Notes

  • Tab list semantics — The container uses role="tablist", each control uses role="tab", and each panel uses role="tabpanel".
  • Named tab list — Each tablist carries aria-labelledby pointing at its section heading, so the two sets are distinguishable.
  • Selection state — The active tab carries aria-selected="true"; the others carry aria-selected="false".
  • Tab to panel association — Each tab uses aria-controls to reference its panel, and each panel uses aria-labelledby to reference its tab. The fourth set deliberately omits that panel name, for the reason given under Screen Reader Findings.
  • Roving tabindex — Only one tab is in the tab sequence at a time, and it is the tab that last held focus; Tab then moves straight into the panel content.
  • Arrow key navigation — Left and Right wrap through the tabs, Home moves to the first, End moves to the last. These move focus only.
  • Manual activation — Moving focus does not change the panel. The focused tab is selected only when Enter or Space is pressed, or when it is clicked. This lets a screen reader user read every tab label before committing to one, and avoids loading each panel in passing.
  • No panel tabindex — Panels contain focusable links, so they are not added to the tab sequence themselves.
  • Scrolling tab list — The tab list scrolls horizontally instead of wrapping to a second row, so the tabs stay on one line at narrow widths and the panel below does not shift down. Every tab is a focusable control, so the browser scrolls the focused tab into view on its own and the scroll container needs no tabindex of its own, which would otherwise add a stop that announces nothing.
  • Visible focus — Tabs and links show a :focus-visible outline that does not rely on color alone. On the tabs it is drawn inside the control, using a negative outline-offset, because a scroll container clips anything painted outside its edge and an offset ring would be cut off.
  • Selection not by color alone — The selected tab is marked by an accent bar, a border, and a background change, not hue alone.
