Tab Navigation

Two tab sets built on the ARIA tabs pattern. Each has five tabs, and each tab panel holds a list of five links. The two sets are identical except for one detail: in the second set every list carries aria-labelledby pointing at the tab that owns its panel, so the list is announced with a name. Compare how a screen reader reports the two.

WCAG 2.2 guidance

The lists in these panels have no accessible name. A screen reader announces only “list, 5 items”.

ARIA Authoring Practices

The lists in these panels use aria-labelledby referencing their own tab, so each list is announced with the tab's name.

Screen Reader Findings

Manual testing on the second tab set, where each list carries aria-labelledby pointing at its own tab, found different results in NVDA and VoiceOver.

  • NVDA — Announces the tab's label twice: once for the tabpanel, which is also named via aria-labelledby referencing the tab, and again for the list nested inside it. The two overlapping names produce a duplicate announcement rather than one clear name.
  • VoiceOver — Does not announce a name for the list at all; aria-labelledby on the <ul> appears not to be honored. VoiceOver also does not announce the tabpanel's own accessible name when focus enters it, unlike NVDA, which does announce the panel name on entry.

Accessibility Notes

  • Tab list semantics — The container uses role="tablist", each control uses role="tab", and each panel uses role="tabpanel".
  • Named tab list — Each tablist carries aria-labelledby pointing at its section heading, so the two sets are distinguishable.
  • Selection state — The active tab carries aria-selected="true"; the others carry aria-selected="false".
  • Tab to panel association — Each tab uses aria-controls to reference its panel, and each panel uses aria-labelledby to reference its tab.
  • Roving tabindex — Only one tab is in the tab sequence at a time, and it is the tab that last held focus; Tab then moves straight into the panel content.
  • Arrow key navigation — Left and Right wrap through the tabs, Home moves to the first, End moves to the last. These move focus only.
  • Manual activation — Moving focus does not change the panel. The focused tab is selected only when Enter or Space is pressed, or when it is clicked. This lets a screen reader user read every tab label before committing to one, and avoids loading each panel in passing.
  • No panel tabindex — Panels contain focusable links, so they are not added to the tab sequence themselves.
  • Scrolling tab list — The tab list scrolls horizontally instead of wrapping to a second row, so the tabs stay on one line at narrow widths and the panel below does not shift down. Every tab is a focusable control, so the browser scrolls the focused tab into view on its own and the scroll container needs no tabindex of its own, which would otherwise add a stop that announces nothing.
  • Visible focus — Tabs and links show a :focus-visible outline that does not rely on color alone. On the tabs it is drawn inside the control, using a negative outline-offset, because a scroll container clips anything painted outside its edge and an offset ring would be cut off.
  • Selection not by color alone — The selected tab is marked by an accent bar, a border, and a background change, not hue alone.
